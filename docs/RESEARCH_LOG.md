# 전체 연구 과정

기준일: 2026-10-22. 이 문서는 보관 코드·프로토콜·결과에 근거한 연구 연대기다. 실제 비공개 대화의 전사본이 아니며 개인 대화·운영 로그를 포함하지 않는다. 정확한 구현·수치는 연결된 원본 파일에서 확인할 수 있다.

## 0. 출발점: 긴 프롬프트와 연구 범위

SOOM Life의 대화 맥락에 현재 질문과 무관한 오래된 대화, 과거 요약과 최근 대화의 중복, 작업 메모, 실행 상태, 도구 설명과 운영 규칙이 함께 들어가는 문제가 출발점이었다. 단순히 “프롬프트가 여전히 길다”는 모델의 자기 보고만으로 이전 대비 토큰 감소량이나 실제 주입 내용을 확정할 수는 없다. 그것은 조사할 단서였고 측정 결과는 아니었다.

초기 운영 개선 방향은 오래된 원문 주입을 줄이고 보관·검색으로 옮기기, 현재 주제와 관련된 메모를 선택하기, 도구 상세 설명을 필요할 때 불러오기, 반복 규칙을 합치기였다. 이후 논점은 고정 길이보다 적응형 예산, 표면 중복보다 의미 중복, 관련성보다 질문에 충분한 근거로 이동했다.

사용자는 그 시점의 운영 방식을 유지하면서 학술 목적으로 더 연구하기로 결정했다. 이 저장소는 **그 이후의 오프라인 연구 전체**를 보관한다. 초기 운영 패치의 소스·운영 DB·배포 로그는 포함하지 않으며, 이 실험들의 성과를 과거 배포의 실측 개선으로 간주하지 않는다.

목표는 길이 최소화 하나가 아니다. 현재 메시지와 인접 대화, 아직 끝나지 않은 요청, 최신 정정, 실제 실행을 입증하는 결과, 필요한 관계 맥락과 권한 규칙을 지키면서 질문에 불필요한 이력을 줄이는 것이다. 다섯 연구 단계는 이 큰 문제의 일부를 작은 모형으로 떼어 검증했다.

## 1. Phase 01 — 의미 coverage를 잘 최적화하면 되는가

자료: [코드](../research/experiment.py), [결과](../research/results.json), [원래 보고서](../research/research.html), [노트북](../research/research.ipynb).

### 가설과 모델

보호된 맥락 P와 현재 질문 q를 고정하고, 과거 대화의 각 항목에 생략·색인·요약·원문이라는 표현 선택지를 두었다. 질문에 필요한 사실 f마다 중요도와 표현별 coverage를 부여하고, 보호 맥락이 이미 제공한 내용을 빼서 **추가로 얻는 정보**를 점수화했다. 목표는 `추가 coverage − λ × 비용`이다.

7개 선택 항목의 4가지 표현은 16,384개 조합이라 작은 문제에서는 정확히 전수 탐색할 수 있었다. 기존처럼 항상 요약이나 색인을 남기는 정책과 달리 생략 자체도 선택지가 될 수 있음을 모형화했다. 다만 이 coverage와 중요도는 자연어에서 추정한 진실이 아니라 실험자가 제공한 값이다.

### 확인한 수학과 반례

- 고정된 비음수 가중 max-coverage는 단조 부분모듈러다. 이미 덮은 사실이 많을수록 같은 항목의 추가 이익이 작아진다.
- 이것을 실제 답변 효용의 일반 법칙으로 확장할 수 없다. XOR에서는 A와 B가 각각 답을 전혀 알려주지 않지만 함께 있으면 답을 결정한다. 관계·부정·상대 변경에도 이런 보완성이 생길 수 있다.
- 공통 요약 프레임 비용이 있으면 단일 항목의 이익이 음수여도 둘을 묶으면 이익이 양수가 될 수 있다. 단순 “양의 한계 이익만 추가” 방식이 실패하는 작은 반례를 만들었다.
- 후보와 비용이 고정되어 있고 정확히 최적화한다면 λ가 증가할 때 선택된 비용은 증가하지 않는다. 실제 운영에서 후보 생성·점수·보호 규칙이 바뀌면 이 결론을 그대로 쓸 수 없다.
- 모든 후보 점수의 오차가 ε 이하라면 추정 점수로 선택한 해의 실제 regret는 2ε 이하라는 경계를 얻는다. 자연어에서 ε를 안다는 뜻은 아니다.

### 점수 오차 실험

80개 합성 세계, 세계당 1,024개 조합, 5개 잡음 수준으로 총 400개 조건을 계산했다. 검색은 정확하게 수행하고 의미 점수만 흔들었다. ε 경계와 regret 경계는 모두 확인되었지만, 이는 의미 점수의 품질을 따로 확보하지 않으면 좋은 조합 탐색만으로 해결되지 않는다는 결과였다.

**다음 단계로 넘어간 이유:** 최적화 자체보다 “정말 필요 없는 근거를 구별하는가”가 문제였다. 임의의 미래 질문을 모두 보존하는 짧은 요약은 일반적으로 불가능하므로, 질문별 선택과 보관된 원문 접근을 분리해서 생각해야 했다.

## 2. Phase 02 — 근거를 남기고, 확신이 없으면 줄이지 않기

자료: [실험](../research/phase02/study.py), [전체 합성 fixture](../research/phase02/fixtures.json), [결과](../research/phase02/results.json), [연결 진단](../research/phase02/link_diagnostic.json), [진단 코드](../research/phase02/diagnose_links.py).

### 설계

한국어 합성 이력에 질문, 답변에 필요한 근거 묶음, 참조 연결을 붙였다. calibration 512개, 같은 생성기의 test 512개, 분포를 바꾼 stress 512개를 만들었다. 근거의 선택 여부를 평가했으며 실제 LLM에 답을 생성시키지는 않았다.

어휘 기반 선택, 최신 대화 보호, 주어진 연결을 따라 추가 근거를 남기는 정책을 비교했다. “필수 근거의 각 절 중 하나 이상의 출처가 남아 있는가”가 실패 판정이었다. 바이트 비용은 **선택한 내용의 UTF-8 크기**였다. 프롬프트 전체 고정비·도구 스키마·토크나이저 비용은 포함하지 않았다.

### 관측과 통계적 보류

어휘 선택은 test에서 내용 바이트를 68.568% 줄였지만 **46/512건**에서 필요한 근거를 놓쳤다. 최신 질문과 어휘가 겹치지 않는 후속 정정·완료 문장이 문제였다. 자식에서 부모 방향으로 연결만 따라가도, 그 자식을 처음부터 검색하지 못하면 해결되지 않는다.

2개 방법 × 11개 threshold의 22개 후보 정책에 대해 보정 집합의 오류와 수락 수를 사용했다. 한쪽 정확 이항 상한과 Bonferroni 보정을 적용하여 위험 한도 5%, 전체 유의 수준 5%를 목표로 삼았다. **채택된 후보는 없었다.** 오류 0건이어도 충분한 수락 사례가 없으면 낮은 위험을 주장하지 않았다.

22개 후보 기준으로 오류가 0일 때 필요한 수락 수는 5% 위험에 최소 119개, 1% 위험에 최소 606개였다. 이 수치는 명시된 통계 가정과 고정 정책군에 관한 계산이다. 같은 저자의 템플릿 변형 데이터를 독립 실세계 표본으로 바꾸는 마법은 아니다. 전체 평균 위험이 낮아도 드문 유형에서는 위험이 100%일 수 있다는 반례도 유지했다.

### 사후 진단: 정답 연결을 양방향으로 제공하면

실패 원인을 본 다음, 동일 fixture에 **정답 연결**을 제공하고 양방향 closure를 적용했다. 이 결과는 새 독립 평가도, 자동 관계 추출의 성과도 아니다.

| 누락시킬 연결의 확률 | test 실패 / 512 | stress 실패 / 512 |
|---:|---:|---:|
| 0% | 0 | 0 |
| 25% | 15 | 55 |
| 50% | 28 | 134 |
| 100% | 46 | 259 |

연결이 전부 있을 때 내용 바이트 감소는 test 67.490%, stress 58.830%였다. 연결 누락 확률은 각 연결의 해시로 결정한 masking 조건이며 실제 누락 비율이 정확히 그 백분율인 것은 아니다.

**다음 질문:** 정확한 연결이 도움이 되는 것은 확인했지만, 자연어 원문에서 그 연결을 안전하게 만들 수 있는가?

## 3. Phase 03 — 원문만으로 연결 만들기, 그리고 평가 자체를 의심하기

자료: [추출기](../research/phase03/extractor.py), [fixture 생성기](../research/phase03/fixtures.py), [평가](../research/phase03/evaluate.py), [동결 프로토콜](../research/phase03/frozen_protocol.json), [원래 결과](../research/phase03/results.json), [라벨 감사](../research/phase03/label_audit.json).

### 입력 경계와 동결

추출기는 순서가 있는 opaque ID와 원문만 입력받는다. 질문 기반 검색을 결합하지만 정답 연결, 필요한 근거 라벨, family 이름을 추출기에 넘기지 않는다. 개발 72개, heldout 288개, stress 288개를 만들었다. 9개 family의 구조는 같은 저자가 설계했고 표현·대상 변형을 나누었으므로 블라인드 외부 평가가 아니다.

개발 후 추출기·fixture·평가 코드의 SHA-256을 동결했다. 동결 시각은 2026-10-22 07:18:36 UTC다. 이후 heldout과 stress를 실행했고, 라벨 감사는 원래 코드를 바꾸지 않고 별도 파일에 추가했다.

### 방법

문자 bigram 유사도와 제한된 한국어 문법을 사용했다. 요청 문장과 변경 문장을 인식하고, 엔터티·대상 단서를 추출했다. 비교 방법은 가장 가까운 요청, 유사도가 높은 요청, 그리고 후보가 유일할 때만 연결하고 그렇지 않으면 보류하는 selective였다.

선택 단계는 최신 문장과 과거 검색 결과에서 시작해 확인한 연결을 따라간다. `selective_with_candidates`는 모호한 변경 문장과 가능한 부모 후보들을 함께 보존한다. **모든 후보를 참 관계라고 주장하지는 않는다.** 이것은 정보 손실을 줄이기 위해 모호성을 남기는 정책이다.

### 원래 결과

heldout에서 selective는 연결 192개를 주장했고 모두 정답이었다. 하지만 해결 가능한 연결 224개 중 192개만 찾아 recall은 85.71%였다. 모호한 64개에는 단정하지 않았으며 새로운 완료 표현 32개를 놓쳤다. 높은 precision이 전체 근거 보존을 뜻하지 않았다.

stress에서는 주장한 96개 연결은 맞았지만 recall은 42.86%로 떨어졌다. 모호한 64개 중 모든 후보가 남은 것은 32개뿐이었다. 요청 자체를 인식하지 못하면 올바른 후보 집합도 만들 수 없었다. 가장 가까운 요청이나 유사도에 강제로 연결하는 방법은 모호성에 잘못된 단정을 더했다.

후보 보존 방식의 원래 근거 실패는 heldout 32/288, stress 128/288이었다. 내용 바이트 감소는 각각 42.093%, 47.727%였다.

### 사후 라벨 감사

실패 사례를 읽으면서 평가가 과도한 요구를 한다는 사실을 발견했다. “A 보고서의 현재 상태”를 묻고 변경 문장이 A 보고서를 명시한다면, 그 문장만으로 현재 상태를 알 수 있다. 최초 요청까지 반드시 남기라는 원래 라벨은 답변 근거보다 **이력 연결의 보존**을 평가했다.

`explicit_task`, `novel_expression`, `cancelled`에서 split별 96개 라벨을 저자가 사후 수정했다. 원래 결과는 보존하고 수정 기준의 결과를 나란히 보고했다.

| 같은 후보 보존 정책 | 원래 이력 기준 | 수정한 현재 답변 근거 기준 | 비용 변화 |
|---|---:|---:|---|
| heldout 288개 | 32 실패 | 0 실패 | 없음 |
| stress 288개 | 128 실패 | 96 실패 | 없음 |

**0/288은 새 알고리즘의 개선이나 독립 검증 결과가 아니다.** 같은 출력이 다른 평가 기준에서 통과한 것이다. 수정 라벨도 외부 판정자의 독립 검증을 받지 않았다.

관측 이력은 완전히 같은데 “그 작업”이 A 또는 B를 가리키는 두 세계가 모두 가능하면, 어떤 선택기도 추가 정보 없이 둘을 구별할 수 없다. 두 세계를 동일 확률로 둔 제한된 예에서는 강제 단일 선택 오류가 최소 1/2이다. 그래서 모호성 보존 또는 질문이 알고리즘의 정상 결과가 되어야 한다.

**다음 단계로 넘어간 이유:** 평가 대상부터 질문에 맞춰 정의해야 했다. 필요한 것은 모든 관계를 보존하는 요약이 아니라 **그 질문의 답을 바꿀 가능성을 제거한 근거**였다.

## 4. Phase 04 — 적응형 예산을 ‘최소 충분 근거’로 정의하기

자료: [의미 모형](../research/phase04/model.py), [최적화 실험](../research/phase04/study.py), [동결](../research/phase04/protocol.json), [결과](../research/phase04/results.json), [별도 구현 감사](../research/phase04/audit.py), [감사 결과](../research/phase04/audit.json).

### 유한 세계와 충분성

초기 시간 2종, 최초 표현 2종, 첫 변경 5종, 둘째 변경 5종, 무관한 문장 2종으로 200개 세계를 만들었다. 기록은 5개이며 변경에는 절대 지정, 상대 +1, 인용된 비행동, 변경 없음이 있다. 질문은 현재 시간, 전체 변경 과정, 최초 요청 원문 인용의 3개다. 200세계 × 3질문 = 600개 짝지어진 사례이며 독립 자연어 표본 600개가 아니다.

선택한 원문·순서·선택적 참 인덱스와 양립하는 **모든 세계가 같은 답을 내는 경우**를 충분하다고 정의했다. 32개 원문 부분집합 × 인덱스 모드 3개를 정확히 탐색했다. 인덱스는 없음, 마지막 상태 사건, 전체 상태 사건 목록이다. 최적화기는 정답 세계와 정확한 의미를 알고 있으므로 oracle다.

선택 마스크 자체로 답을 암호처럼 전달하는 것은 허용하지 않았다. 생략했다는 사실만으로 “생략된 문장에는 변경이 없다”라고 추론하지 않는다. 렌더링한 원문, 출처 라벨, 인덱스, 줄바꿈의 UTF-8 비용을 계산하고 고정 보호 대화·질문은 따로 보고했다.

현재 시간의 최소 충분 비용은 세계에 따라 96~318 bytes였다. 96을 고정 예산으로 삼으면 120/200세계에서 불충분했다. 318은 이 유한 모형 안에서는 충분하지만 일반 대화에 대한 보장값이 아니다. 적응형 예산은 임의의 길이 함수를 만드는 대신 충분성 제약을 만족하는 가장 작은 비용의 결과로 이해할 수 있었다.

### 반례와 감사

- 최신 상태 문장만 남기면 120/200세계에서 부족했다. 정확한 마지막 사건 인덱스를 추가해도 상대 변경 때문에 56/200세계가 부족했다.
- 현재 시간에 충분한 최소 선택을 “변경 과정” 질문에 재사용하면 128/200세계가 불충분했다.
- 실제 10 → 12 → 14인데 마지막 사건 인덱스를 잘못 주면 모형은 12를 유일한 답으로 판정할 수 있었다. 잘못된 전제를 넣은 논리적 확실성은 사실 정확성이 아니다.
- record 4까지의 참 snapshot 이후 record 5에서 16시로 변경하면, 이전 snapshot은 그 시점의 증거일 뿐 현재 최신 상태가 아니다.

별도 목록 기반 구현과 bitset 구현으로 1,800개 최적해 비교를 했다. 집합 덮개와 충분성의 동치, 반사실 coverage의 단조 부분모듈러성, ID·무관한 문장 불변성을 검사했다. 두 구현은 같은 저자의 같은 유한 모형이므로 외부 경험 검증은 아니다. 동결 시각은 07:45:15 UTC다.

## 5. Phase 05 — 역방향 의존성과 필요한 부분만 상세 해석하기

자료: [v1 엔진](../research/phase05/engine.py), [fixture](../research/phase05/fixtures.py), [실험](../research/phase05/study.py), [프로토콜](../research/phase05/protocol.json), [결과](../research/phase05/results.json), [구체 실행 감사](../research/phase05/audit.json).

### 의미 계약

두 모임의 시간·장소, 총 4개 필드를 다루는 제한된 계획 언어다. 명시적 지정, 정수 시간 이동, 다른 모임의 시간 복사, 둘 중 하나의 모호한 변경, 명시적 인용·비행동을 표현한다. 질문도 한 모임 시간, 한 모임 시간·장소, 두 모임 시간으로 제한했다. 변경 이력 질문은 지원하지 않고 전체 이력을 돌려준다.

엔진은 기록의 순서·opaque ID·원문, 공개 엔터티 목록, 질문, 완전한 snapshot head와 digest만 받는다. family·split·gold transition은 받지 않는다. **계획 상태**이며 실제 캘린더 반영이나 도구 실행 완료를 해석한 것이 아니다.

저렴한 정규 문법과 추가 표현을 아는 상세 문법을 나눴다. 둘 다 못 읽는 문장은 `havoc`, 즉 모든 필드를 바꿀 수 있는 사건이다. 알 수 없음을 무관함으로 바꾸지 않는다. 추상 상태는 각 필드의 가능한 값 집합이고 TOP은 제한을 모른다는 뜻이다. 필드별 집합의 곱이므로 필드 사이 상관관계는 잃을 수 있다.

### 알고리즘

1. 질문이 요구하는 필드 집합 D에서 시작한다.
2. 기록을 최신에서 과거 방향으로 한 번 훑는다.
3. 사건이 D에 영향을 주지 않으면 생략한다.
4. 절대 지정은 그 필드의 이전 값 의존성을 끝내고, 상대 변경은 유지한다.
5. A가 B의 시간을 복사하면 그 사건 시점의 B를 새 의존성에 추가한다.
6. 미해석이 현재 필요와 만나는 구간에서만 상세 문법을 호출한다.
7. 필요한 필드가 전부 닫히면 더 오래된 접두부 파싱을 멈춘다.
8. 남은 의미 불확실성이 관련되면 전체 원문으로 fallback한다. 값이 여러 개면 모호성을 남기고, 모든 요구 필드가 singleton이면 `certified_model`이다.

보존하는 것은 정의한 의미 모형의 답이지 자유 한국어의 모든 의미가 아니다. snapshot 무결성 검사는 먼저 전체 바이트를 읽는다. 따라서 역방향 파싱이 빨리 멈춰도 전체 archive I/O가 sublinear라는 주장은 하지 않는다.

### 실험 규모와 비교군

동결은 08:17:00 UTC다. main은 12 family × 16이력 × 2질문 = 384질문, stress는 12 × 12 × 2 = 288질문이다. 총 336개 이력, 672질문이다. 같은 저자가 문법과 fixture를 설계했으며 IID·독립 블라인드 평가가 아니다.

비교군은 미해석을 버리는 `drop_unknown`, 미해석을 보수적으로 남기는 `cheap`, 전체 기록을 상세 해석하는 `eager`, 필요한 구간만 상세 해석하는 `lazy`다.

| main, 384질문 | singleton 판정 | 틀린 singleton 판정 | opaque fallback | 모호성 | 미지원 질문 | 출력 바이트 감소 |
|---|---:|---:|---:|---:|---:|---:|
| drop_unknown | 336 | 112 | 0 | 32 | 16 | 73.09% |
| cheap | 128 | 0 | 208 | 32 | 16 | 31.67% |
| eager | 288 | 0 | 48 | 32 | 16 | 63.13% |
| lazy | 288 | 0 | 48 | 32 | 16 | 63.13% |

main에서 eager와 lazy의 답·상태·선택 기록은 같다. 상세 해석 호출은 **3,140 → 224회**, 92.866% 감소했다. 상세 해석에 전달한 원문은 213,872 → 15,920 bytes였다.

stress에서 drop_unknown은 258개를 singleton으로 판정했지만 그중 126개가 틀렸고 답 포함 위반은 129개였다. conservative 3개 방법은 모두 singleton 36개, opaque 240개, 미지원 12개였다. 틀린 singleton은 관측되지 않았지만 **인증 범위는 12.5%**에 그쳤다. eager/lazy 출력 감소는 **9.207%**이며 상세 호출은 2,562 → 240회로 90.632% 줄었다.

비용에는 receipt·질문·출처를 포함한 렌더링 바이트를 계산했다. 추가로 상세 파서 입력 바이트까지 더한 proxy에서는 main eager 18.059%, lazy 59.775% 감소였으나, stress eager는 **37.211% 증가**, lazy는 4.311% 감소였다. 파서가 실제 LLM이었다면 고정 호출비도 필요하므로 이 값을 실비 절감률로 쓸 수 없다.

### 길이·무결성·새로움의 경계

4,096개 무관한 문장이 마지막 확정 사건 **앞**에 있으면 lazy는 cheap 1회·detail 0회로 필요한 의미를 닫았고 eager는 모든 4,103개를 파싱했다. 같은 문장들이 확정 사건 **뒤**에 있으면 lazy도 cheap 4,097회·detail 4,096회가 필요했다. 상세 문법으로 비행동임을 확인하기 전에는 생략할 수 없기 때문이다. 기록 위치에 따라 비용이 크게 다르다.

기록 삭제·수정·순서 변경은 snapshot 무결성 실패로 검출했다. 그러나 내부적으로 일관된 오래된 snapshot의 답 13과 새 snapshot의 답 22는 둘 다 각각 인증된다. authoritative 최신 head를 따로 받지 않으면 최신성을 알 수 없다.

구체 상태 집합을 실행하는 별도 평가기로 9개 연산의 길이 4 프로그램 6,561개 × 질문 3개 = 19,683개 투영 보존을 확인했다. 이 구체 실행기도 같은 저자의 구현이다.

## 6. Phase 05 확장 — 더 짧게 만들기, 작동하지 않은 검사를 찾아내기

자료: [최초 reducer](../research/phase05/reducer.py), [최초 확장 결과](../research/phase05/reduction_results.json), [실제 결함 진단](../research/phase05/reduction_diagnosis.json), [수정 엔진](../research/phase05/revision02/engine.py), [수정 확장 실험](../research/phase05/revision02/reduction_study.py), [수정 결과](../research/phase05/revision02/reduction_results.json).

### 비용 최적화 가설

의존성만 따라가면 `0시 확정 → +1 → −1`을 모두 남길 수 있다. 중간 값을 아무도 관측하지 않는 현재 상태 질문에서는 최종값이 0이므로 상쇄된 이동을 제거할 수 있다.

같은 필드의 정수 이동을 독립 구간으로 묶고, 총 이동량이 같은 원문 부분집합 중 바이트 비용이 최소인 것을 동적 계획법으로 찾았다. 다른 필드의 독립 변경은 사이에 있어도 된다. 그러나 복사·읽기·절대 대입·모호한 변경·미해석이 해당 필드를 건드리면 구간을 끊는다. 예를 들어 +1 뒤 B가 A를 복사하고 −1을 하면 B가 중간 값을 봤으므로 상쇄 제거가 불가능하다.

최적성은 **허용한 독립 정수 변경 구간 안의 부분집합**에만 성립한다. 모든 대화, 여러 표현 선택, 전체 의존성 그래프, 변경 과정 질문에 대한 전역 최소 비용이 아니다.

### 최초 실험의 실패

첫 확장 결과는 14,641프로그램 × 3질문 = 43,923개 투영 보존, 1,364개 DP 대 완전탐색 비교를 통과했지만 **추가로 줄어든 질문이 0개**였다. 단순히 “보존 검사를 모두 통과”했다고 성공으로 보고할 수 없었다.

원인을 추적하니 `(뒤|앞)로`라는 문법이 `뒤로`는 읽지만 `앞으로`를 읽지 못했다. 음수 이동이 `havoc`가 되어 원래 상쇄 예시는 `opaque_fallback`으로 떨어졌다. 앞선 `audit.json`의 최소 비용 반례는 그 상태를 기록하지 않았으므로, 그것만으로 실제 인증된 backward slice가 상쇄에 실패했다고 주장하면 과장이다. **이 해석 정정이 원본 파일보다 우선한다.** 원래 파일과 결과는 지우지 않았다.

### revision02와 더 강한 검증

엔진 문법을 `(뒤로|앞으로)`로 수정한 별도 revision을 만들었다. 버전 표기도 바꾸었다. 08:26:12 UTC의 새 프로토콜에 수정 코드와 검사 계획을 동결했다.

추가한 검사는 의도한 연산 11개의 parser round-trip, 상쇄 예시가 `certified_model`인지, 선택이 [0,1,2] → [0]으로 실제 줄어드는지, 전체 프로그램 중 축소가 한 번 이상 있는지다. 보존만 하는 vacuous pass를 막았다.

| 수정 실험 | 결과 |
|---|---:|
| 길이 4, 11개 연산 프로그램 | 14,641 |
| 구체 투영 비교 | 43,923, 모두 보존 |
| 실제로 더 짧아진 질문 | 2,936 |
| 총 출력 bytes | 15,434,306 → 15,061,306 |
| 총 추가 감소율 | 2.416694% |
| signed-sum DP 대 전수 부분집합 비교 | 1,364, 모두 일치 |
| 중간 copy-read 장벽 | 보존 |
| 인증된 상쇄 예시 | 366 → 241 bytes |

별도 [corpus regression](../research/phase05/revision02/corpus_regression.json)에서 기존 672질문 × 4모드 = 2,688개 출력·상태·비용 비교가 기존과 같았다. 그 corpus에는 `앞으로` 표현이 없기 때문에 이 회귀 검사가 새 문법을 검증하는 것은 아니다. 새 연산 suite가 그 역할을 한다.

### 유리하지 않은 결과도 남기기

같은 reducer를 기존 672질문에 적용하면 **추가 축소 0건**, 상세 파싱 **80회 / 4,112입력 bytes 증가**였다. 동결 엔진이 내부 AST cache를 내보내지 않아 선택한 원문을 다시 파싱하는 비용을 기록한 것이다. 기존 corpus는 반복 상쇄 구조를 풍부하게 포함하지 않는다. 따라서 reducer의 수학적 정확성이 곧 일반적인 실용 이득을 뜻하지 않는다.

정수 이동의 크기가 커지면 DP의 reachable sum 수가 커진다. `O(mR)` 상태 갱신은 수치 크기에 의존하는 의사다항 비용이고, 구현의 경로 tuple 복사 비용도 추가된다. 실제 운영에서 항상 빠르다는 결론은 없다.

## 7. 현재 합의와 다음 경계

가장 지지되는 방향은 **질문별 답의 보존 계약 + 필요한 필드의 역방향 의존성 + 불확실성을 남기는 의미 해석**이다. 상쇄 DP는 특정 구조의 보조 최적화다. 현재 가장 큰 한계는 모르는 문장을 모두 전역 영향으로 처리하여 stress에서 fallback이 많다는 점이다.

다음 연구는 그 영향 범위를 안전하게 좁힐 수 있는지와, 완전한 의미 해석 전에도 필요한 정보만 얻을 수 있는지에 집중할 가치가 있다. 이것은 아직 가설이며 [다음 실험 계획](NEXT_EXPERIMENT.md)에 실행 전 판정 기준을 적었다.

실제 LLM 품질, 실제 토큰, 회수·해석·검증·답변까지의 전체 비용, 외부 작성자의 자연어 평가, 최신 archive head 연동, 실제 실행 결과의 권한·출처 의미는 모두 남은 과제다. 이번 저장소 게시로 그 과제가 완료되었다고 주장하지 않는다.
