# 사후 분석: 파서 실행 감소와 전체 이득 사이의 정확한 경계

이 문서는 **동결한 주평가 후** 작성했다. [POSTHOC_PROTOCOL.md](POSTHOC_PROTOCOL.md)를
별도로 기록하고 코드와 함께 [posthoc/freeze.json](posthoc/freeze.json)에 hash를 남긴 뒤
[cost_boundary_probe.py](cost_boundary_probe.py)를 실행했다. 주평가의 알고리즘·자료·결과와
가설 판정은 바꾸지 않았다. 유리한 길이를 포함한 이 자료는 독립 평가가 아니다.

## 1. 주평가의 실패가 뜻하는 범위

주평가에서 실제 파서 실행은 2,292→750회였지만 P7은 2,093,235→4,341,013으로 늘었다.
이는 현재 workload에서의 실패다. 모든 가능한 원문과 반복에서 캐시가 손해라는
정리는 아니다. [THEORY.md](THEORY.md)의 사전 비용식은 오히려 세 단계를 거치는
긴 원문에 조건부 이득이 가능함을 보여준다. 주평가의 긴 quote는 주로 cheap 단계에서
끝나고, 가장 긴 parameterization은 용량을 넘는다. 따라서 긴 deep quote의 조건을
추가로 구성하여 **이미 고정된 비용식의 예측**을 검사했다.

원문 하나에서 요청한 단계 수를 m, 원문 길이를 L, context 길이를 C, hit에서
재사용한 stage payload 길이 합을 R이라 하자. 완전히 warm인 기록에서 원래의
`mL` 파서 입력을 없애지만 key 생성 L, probe C+L, payload read R을 지불한다.

\[
\Delta P_7=L+(C+L)+R-mL=(2-m)L+C+R.
\]

이 식에는 질의당 context encoding이 아직 빠져 있다. m=1,2이면 이 식부터
양수다. m=3이면 `L>C+R`일 때 기록 단위 warm 이득이 가능하다. cold 구축,
다른 기록, eviction, 전체 snapshot 검증과 출력까지 계산해야 stream의 이득을 말할 수 있다.

## 2. 의미가 같은 두 표면형, 다른 해석 비용

기록은 두 개다. 첫 기록은 `가람.time=8`을 설정하고, 두 번째는 상태를 바꾸지 않는
quote다. 동일한 time 질문을 T=8번 한다. 각 cell은 빈 캐시에서 시작한다.

```text
cheap quote: 예시일 뿐이야:「...」 실제 변경은 없어.
deep quote:  표현 연습:「...」라는 문장을 써봤어. 약속은 그대로야.
```

두 quote의 의미는 noop이지만 동결 파서는 전자에 1단계, 후자에 3단계를 요청한다.
본문은 한글 `가`를 n회 반복한다. n은 실행 전 `0,32,128,512,2048,8192,24000`으로
정했고, deep 조건에서 두 용량 경계의 양쪽 정수값도 산술로 추가했다.
18 cell × 8질문 = 144질문이다. 시간은 이 진단에서 측정하지 않았다.

이번 context 길이 C=101, set 원문 S=45, set payload r_s=78이다.
cheap quote는 `L=51+3n`, payload r_q=69, m=1이다.
deep quote는 `L=71+3n`, payload r_q=154, m=3이다. 아래에서 R=r_s+r_q로 쓴다.
여기서 R은 **두 기록의 합**이며 위 기록 하나의 식에 있는 R과 범위를 구분한다.

## 3. 두 항목이 함께 들어가는 영역

캐시 항목의 논리적 크기는 `e_s=C+S+r_s`, `e_q=C+L+r_q`다.
두 항목의 합이 65,536 bytes 이하이고 entry 수도 한도 안이면 최초 query만 miss다.
첫 질의와 후속 질의의 P7 차이는 각각

\[
\Delta_{cold}=5C+3(S+L)+2R,
\]

\[
\Delta_{warm}=3C+S+(2-m)L+R.
\]

첫 식은 context 생성 C, 두 raw key 생성 S+L, 두 probe 2C+S+L,
payload encoding R, 두 write 2C+S+L+R의 합이다. cold에서는 원래 파서 실행을
전혀 절약하지 못한다. 후속 질의는 두 key와 probe, payload read를 지불하면서
set의 S와 quote의 mL 파서 입력을 절약하므로 두 번째 식을 얻는다.

deep(m=3)의 T회 총 차이는

\[
\Delta_T=(3T+2)C+(T+2)S+(4-T)L+(T+1)R.
\]

따라서 이 두 기록·고정 순회 모형에서는 **T≤4이면 길이를 늘려도 총이득이 불가능**하다.
T=8이면

\[
\boxed{\Delta_8=26C+10S-4L+9R=5164-4L.}
\]

후속 질의만의 이득은 `L>580`에서 가능하지만, 8회 전체 이득은 **L>1291**에서
비로소 가능하다. warm 한 번의 이득과 cold부터 전체 이득은 같은 조건이 아니다.
cheap 조건은 `Δ8=26C+10(S+L)+9R>0`이므로 이 영역에서도 손해다.

## 4. 용량을 넘는 두 가지 영역

### 4.1 각각은 들어가지만 함께는 못 들어갈 때

조건은 `e_q≤65536<e_s+e_q`다. query는 뒤에서 앞으로 quote→set 순서로 방문한다.
첫 query 뒤에는 set만 남는다. 다음 query의 quote가 set을 밀어내고, 그 다음
set이 quote를 밀어낸다. 이 순서가 반복되어 매 query가 cold다.

\[
\Delta_8=8\Delta_{cold}>0.
\]

entry 제한 64는 이 예에서 활성화되지 않는다. **두 항목의 바이트 합과 순회 순서**가
필요한 가정이다. 모든 LRU workload가 이와 같이 행동한다고 일반화하지 않는다.

deep quote에서는 둘 다 들어가는 마지막 본문 길이가 n=21662, L=65057이다.
`e_s+e_q=65536`으로 한도에 정확히 맞는다. 한글 한 글자, 즉 3 UTF-8 bytes를 더하면
L=65060이고 합이 65539가 되어 상호 축출 영역으로 들어간다.

### 4.2 quote 하나도 보관할 수 없을 때

`e_q>65536`이면 oversized quote를 저장하지 않고 set만 보관한다.
quote의 세 단계는 매번 실행된다. 그래도 quote의 key 준비·probe·payload 크기 계산은
현재 구현에서 수행하므로 비용이 사라지지 않는다.

\[
\Delta_{cold,os}=4C+3S+2L+2r_s+r_q,
\]

\[
\Delta_{warm,os}=3C+S+2L+R.
\]

deep에서는 n=21736, L=65279까지 quote 하나가 들어가고, n=21737, L=65282부터
oversized다. 이때 set의 재사용은 회복되어 8질문의 실제 실행 수가 32→25로 줄지만
P7은 여전히 증가한다. 개별 항목을 저장할 수 있는지와 두 항목을 함께 저장할 수
있는지는 다른 경계다.

## 6. 이 결과가 지지하는 것과 지지하지 않는 것

이 결과는 **정확한 재사용과 실제 계산 감소만으로 총이득을 결론낼 수 없고,
단계 수·원문 길이·초기 비용·함께 보관해야 할 크기를 같이 보아야 한다**는
주장을 지지한다. 위 식은 선택한 동일 가중 P7 proxy와 동결 구현의 정확한 관계다.
실제 CPU·메모리 버스·LLM 비용에 대한 보편적 하한이 아니다.

긴 deep quote의 조건부 이득을 의도적으로 구성했다. 그러므로 −12.23%를
새 평균 성능으로 발표하거나 주평가 +107.38%를 교체하지 않는다. 이 진단은 시간도
측정하지 않아 해당 조건의 속도 개선을 주장할 수 없다. 다음 정책 설계에 이 자료를
쓰면 이미 개발 자료가 되므로 별도의 새 평가가 필요하다.
